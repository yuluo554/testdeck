## 一、介绍

**痛点**：CI 页面只回答"这一次 run 红不红"。开发者真正要回答的是另外三个问题：**谁在抖**（同一用例在多次 run 之间 pass/fail 交替）、**谁在变慢**（同一用例 p50/p95 跨版本抬升）、**这次是不是新坏**（当前 run 的失败是不是上一轮没有的）。这三件事都需要**多次 run 的本地历史**，而大多数团队的历史散落在 CI 的临时 artifact 里：过期即删、按 run 隔离、不能跨 run 查询，也不能用键盘逐条下钻到 failure 原文。把 JUnit XML 下载下来之后，通常只剩"解压 → 用浏览器打开某个 run 的 HTML 报告"这一条路，跨 run 的比较仍要手工做。

**需求侧证据（✅ 已核对，原话直连；基准日 2026-10-17）**：

- "I maintain an OSS project with a very involved CI setup… worth having observability into which tests are flaky… takes junit.xml exports from **cargo nextest, vitest, playwright, pytest, and go test**. What do you all recommend?"（Ask HN，vrm，2025-09-12）https://news.ycombinator.com/item?id=45222181
  —— 多框架 JUnit XML 已经是事实标准输入；提问者要的是**跨 run 的可观测性**，不是又一个单次报告页。
- "There is really **no proper way to expose the results if you are not using Jenkins** as your main CI."（rasjani，2022-10-26）https://news.ycombinator.com/item?id=33341434
  —— 结果展示被 CI 平台绑定；离开平台就没有本地归档层。
- "people often take flaky test way less serious then they should… written off as flaky tests"（dathinab，2026-04-20）https://news.ycombinator.com/item?id=47837206
  —— "flaky" 常被当成噪声写掉，缺少可复查的量化记录。
- "Flaky tests are a very strong signal of a bug, somewhere. Problem is it's not always easy to tell if the bug's in the test or in the code under test."（tomjakubowski，2026-04-20）https://news.ycombinator.com/item?id=47839948
  —— 需要把"抖动"与"恒失败"分开看，而不是把所有非绿都叫 flaky。

**相邻已占位但形态不同（✅ 仓库页，基准日 2026-10-17）**：

- `allure2` **5564★**：Java/Web 报告体系，重（需要报告服务或静态站点生成流程），不是终端内下钻。
- `ctrf` **100★**：JSON 报告标准，解决"报告格式统一"，不含 TUI、不含跨 run 本地库。
- `FlakeHarbor` 2★ / `kare` 1★：纯 CLI，输出 flaky 列表，无交互下钻、无三栏视图、无慢测试瀑布。

**判定**：赛道有真实工具，但"**本地 + 多 run + 键盘下钻**"的终端形态为空（⬜ 软论据）。本题与 allure2 的差异是**形态与重量**（终端内即时下钻 vs 报告站点），与 FlakeHarbor/kare 的差异是**交互与分型**（三栏视图 + 恒失败不计入 flaky + 慢测试瀑布）。

**技术可行性（✅）**：纯本地文件，无 root、无网络、无账号。Playwright、pytest、Go（gotestsum）、Maven Surefire 默认都能产出 JUnit XML，用户零改造成本；`gh run download` 只是可选的 artifact 拉取方式（需要 gh 登录，但非必需）。风险点只有一个：超大 XML（>50MB）必须用 `iterparse` 流式读取，不能整树 `parse`。

**技术选型（✅）**：**Textual**。Tree、DataTable、Sparkline、Footer 均为现成控件；CSS 式布局适合三栏；`Pilot` 可做无头 UI 测试（键盘流程可断言）；`textual run --dev` 便于录屏。Rich 仅用于 `export` 的降级文本输出；手写 ANSI 在 Python 下没有收益。

**独特性拷问（为什么不是"让 LLM 看日志"）**：跨 run 的结论依赖**持久状态**（本地 SQLite 里上千次 run 的 occurrence 矩阵）、**可复现的算术**（flaky 分数、分位数、回归比值）与**进入既有工作流的键盘下钻**。LLM 可以解释一段失败日志，但不会替用户持续归档每次 run，也无法给出可被 CI 门禁复算的确定性数值。

## 二、任务要求

首期 **5 个模块**，扩展项另列。每模块写清 **输入 / 输出 / 确定性纪律 / 验收**。所有模块共享 `data/README.md` §四的数值口径，不得在代码或文案中另立第二套口径。

### 模块①：载入与归一化

- **输入**：显式文件/目录路径；glob `**/junit*.xml`；`target/surefire-reports/*.xml`；`build/test-results/**`；可选的 `gh run download` 目录（已下载到本地）。
- **输出**：本地 SQLite 库 `~/.local/share/testdeck/testdeck.db`（遵循 `XDG_DATA_HOME`），四张表：
  - `runs`：`branch`、`commit`、`ci_run_id`、`started_at`、`source_path`、`framework`、`ingested_at`；
  - `suites`：`run_id`、`name`、`tests`、`failures`、`errors`、`skipped`、`time_ms`、`source_path`；
  - `cases`：用例身份键（`suite_name`、`classname`、`name`），不含逐 run 状态；
  - `occurrences`：`run_id`、`case_id`、`status`（pass / fail / skip / **missing**）、`time_ms`、`failure_message`、`failure_type`、`stack_first_line`。
  - 另输出一次 ingest 摘要（文件数、run 数、用例数、按原因分组的 skipped 文件）。
- **引擎**：`xml.etree.ElementTree.iterparse` 流式解析，兼容 `<testsuites>/<testsuite>/<testcase>` 与 `<failure>`/`<error>`/`<skipped>` 变体；框架识别按根节点属性与文件名，识别失败时记 `framework: unknown` 而不是猜。重复导入同一 `(branch, commit, ci_run_id)` 走 upsert，不产生重复 run。
- **确定性纪律**：run 身份 = `(branch, commit, ci_run_id)`；用例身份 = `(suite_name, classname, name)`（参数化用例保留完整参数串）；耗时统一解析为整数毫秒（十进制秒 → 毫秒，ROUND_HALF_UP）；路径统一为正斜杠并相对扫描根；排序固定（suite 按 XML 出现顺序，class/name 字典序）。`ingested_at` 只作元数据，不进入任何导出或 diff。
- **验收**：pytest、gotestsum、Playwright 三份真实产物的用例数、失败数、skipped 数与各框架自身汇总**逐项相等**；5 万用例单文件解析 < 2s（`iterparse`，基准脚本在 `bench/bench_ingest.py`）；同一目录重复 ingest 后四表行数不变。

### 模块②：失败优先三栏视图

- **输入**：本地 SQLite 库（可选 `--run` 指定某次 run，默认最近一次）。
- **输出**：终端三栏界面。
  - 左栏：`suite → class → test` 树，节点带失败计数（失败优先排序，含 fail 的子树排在前面）；
  - 右上：summary（total / fail / skip / flaky / broken / slow）；
  - 右中：选中用例的 failure 原文、stack 首行、历史 sparkline（最近 N 次 run 的 pass/fail 序列）；
  - 底部：键位栏。键位 `j`/`k` 上下移动、`g`/`G` 首尾、`Enter` 展开或进入、`F` flaky 矩阵、`S` 慢测试瀑布、`D` 两次 run diff、`/` 搜索、`e` 导出当前视图、`?` 帮助。
- **引擎**：Textual `Tree` + `DataTable` + `Sparkline` + `Footer`；查询与渲染分离（`queries.py` 只读 SQL，`app.py` 只组装控件）；大库查询走后台 worker，UI 不阻塞。
- **确定性纪律**：树顺序、summary 计数、sparkline 窗口长度都从单点定义读取；键位表唯一来源 `src/testdeck/keys.py`（Footer、帮助层、测试三处共用）；同一库同一选中项两次打开渲染一致。
- **验收**：`textual.pilot` 无头测试用纯键盘完成"进入应用 → 移动到失败用例 → 读到 stack 首行"全流程，无鼠标事件；summary 各计数与直接 SQL 查询逐项相等。

### 模块③：flaky 矩阵与分型

- **输入**：选定时间窗内的 occurrences（默认全部 run）。
- **输出**：test × run 四态热力矩阵（pass / fail / skip / **missing**），按 flaky 分数降序；每条用例一个分型标签。
- **口径（唯一来源见 `data/README.md` §四）**：
  - `fail_rate = fails / (passes + fails)`；`transitions` = 相邻两次 run 状态均为 pass/fail 且不同；
  - `flaky_score = transitions / (n - 1)`；
  - `fail_rate == 1` → **broken**；`fail_rate == 0` → **stable**；`5% ≤ fail_rate ≤ 95%` 且 `transitions ≥ 3` → **flaky**；其余 → **watch**（观察）；阈值可配。
- **引擎**：SQL 聚合 + Python 分型；分型只做确定性算术，不做任何启发式加权。
- **确定性纪律**：窗口、阈值、`watch` 兜底分型均在规则文件单点定义；同一库两次计算逐值一致；skip/missing 不制造 transition，也不计入 fail_rate 分母。
- **验收**：固定 fixtures 的 flaky 分数与手算逐项一致；**恒失败用例（fail_rate == 1）不得进入 flaky 列表**，该断言写成独立测试（这是与 FlakeHarbor/kare 纯 CLI 列表的差异点）。

### 模块④：慢测试与回归

- **输入**：base run 与 curr run 的 occurrence 耗时；或一个时间窗内的多次 run。
- **输出**：按耗时降序的瀑布条（p50 / p95）；base vs curr 的比值与绝对增量；回归清单。
- **口径（唯一来源见 `data/README.md` §四）**：
  - p50/p95 使用**线性插值**（索引 = `(n-1) * p`，取 floor/ceil 两点线性插值）；
  - 回归判定：`curr_p50 / base_p50 ≥ 1.2` **且** `curr_p50 - base_p50 ≥ 200ms`（两条件同时满足，边界值计入）。
- **引擎**：耗时取整数毫秒；同一用例在窗口内缺失的 run 不计入分位数样本（记 missing，不补 0）；瀑布条宽度按当前列表最大值归一。
- **确定性纪律**：分位数算法、回归阈值、慢测试阈值（`slow_ms`）均单点定义；排序固定（耗时降序，同耗时按用例名）；两次渲染一致。
- **验收**：固定耗时 fixture 的 p50/p95 与独立参照脚本逐值相等；回归判定在 `1.2x` 与 `200ms` 两个边界各有单测（恰好等于、略低于、略高于三种情形）。

### 模块⑤：导出与 CI 门禁

- **输入**：当前视图或指定 run/窗口。
- **输出**：`export --format md`（可直接贴 PR 的表格）与 `export --format json`（机读）；`--fail-on flaky` / `--fail-on new-failures` / `--fail-on regressions` 在命中时返回非零。
- **引擎**：导出与 TUI 共用同一个序列化层（`report_model.py`），TUI 只是它的一个渲染器；JSON 字段即 TUI 字段，md 表格列由同一模型生成。
- **确定性纪律**：md 列顺序、JSON 键顺序固定；不写生成时刻；同一库两次导出逐字节一致。退出码语义：`0` 达标、`1` 门禁触发、`2` 用法错误、`3` 依赖缺失或库不可读（如请求 `--from-gh` 但 `gh` 不存在，必须 exit 3，不得静默当成"没有新结果"）。
- **验收**：样例仓库上三种 `--fail-on` 跑出预期退出码；md 表格字段与 TUI 显示的字段**完全一致**（同一模型的两条渲染路径）；`export --format json` 可被 `jq` 直接消费。

**扩展项（首期不做）**：覆盖率叠加（把覆盖率 XML 与用例树关联）、多仓库聚合（跨库汇总同一用例身份）、历史趋势图（按天/按 commit 的 flaky 与耗时曲线）。三项都依赖首期四表稳定后再加，避免表结构反复迁移。

**招牌动词表（能力名词 → 交付态命令 → 断言基准）**：

| 能力名词 | 哪条交付态命令产出它 | 哪条基准/测试断言它 |
|---|---|---|
| 多框架归一入库 | `testdeck ingest <paths...>` 写入 runs/suites/cases/occurrences | `bench/bench_ingest.py`：三份真实产物用例数/失败数/skipped 逐项相等；5 万用例 < 2s |
| 失败优先三栏树 | `testdeck tui` 左树 + 右上 summary + 右中 failure 原文 | `tests/test_tui_pilot.py`：Pilot 键盘全流程读到 stack 首行 |

- **受众**：维护多框架测试套件的 CI 维护者；需要向团队解释"这条为什么红"的 QA；关心交付节奏的团队 TL；没有 Jenkins 一类统一报告平台的开源维护者。
- **时代性**：测试套件规模与框架数量同时增长，CI 只保留短期 artifact；大模型可以解释单条失败，却不会持续归档每次 run，也不能给出可被门禁复算的确定性数值。
- **开源空白（三行）**：①"JUnit XML 查看器"有真实工具，但以单次报告页为主；②flaky 工具以纯 CLI 列表为主，没有终端内三栏下钻；③"本地 + 多 run + 键盘交互"这一组合在检索中未见产品级结果（⬜ 软论据）。

## 六、边界与非目标

- **不执行测试**：只读 JUnit XML 结果，不调用 pytest / go test / playwright，不管理测试进程。
- **不做 CI 平台对接**：不调用 CI API、不轮询 run 状态；`gh run download` 只是"把已下载目录喂给 ingest"的可选路径。
- **不做覆盖率计算**：覆盖率叠加列为扩展项；首期只处理 JUnit XML。
- **不做云端存储**：纯本地 SQLite，无同步、无账号、无遥测。
- **不做"AI 分析失败原因"**：所有结论都是确定性算术（分数、分位数、比值、状态迁移），不引入模型推断。
- **不做 Web 面板与图形界面**：唯一形态是终端 TUI；`export` 的 md/json 是给 PR 与脚本用的文本出口，不是第二形态。
- **隐私红线**：测试结果可能含日志与路径；全部数据只写本机 SQLite，**零上传、零遥测、无网络请求**；导出文件由用户自行决定去向。
- **品牌隔离**：本题定位为独占的"测试结果终端工作台"；命名、文案、代码命名空间均围绕"run / suite / case / flaky / slow"词系；文档**不提及本系列任何其他项目**。
- **结论纪律**：flaky 与回归是**基于历史数据的测量结论**，不是"一定是代码 bug"的判定；分型标签只描述观测到的状态迁移。
- **首期范围限定**：仅上述 5 个模块；覆盖率叠加、多仓库聚合、历史趋势图留扩展项；首期只保证 JUnit XML 家族，不解析 TAP、CTRF、Allure 原生格式。
